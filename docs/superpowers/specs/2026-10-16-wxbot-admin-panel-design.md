# 微信机器人管理台（admin）设计

日期：2026-10-16
状态：待你确认（确认前不动手）

## 一、为什么做

现在管这个机器人只有两条路：改配置文件，或者在控制台敲命令。

- 配置散在三处、三种写法：多数插件在 `bot_config.json` 的 `plugins.<名称>` 段（扁平键值，例如 `echo.prefix`）；复杂插件自带配置文件（`plugins/bga_plugin/bga_config.json`，嵌套结构，例如 `account.email`、`groups` 群→桌游映射）；大模型密钥又在 `llm_config.json`。
- 「有哪些配置、各自什么意思」只写在每个插件的 README 散文里。代码里只有校验逻辑，机器读不到，页面上就摆不出来。改 bga 插件时你遇到的就是这个：不知道有哪些配置项，也不知道每项是干嘛的。
- 配置改完必须重载插件才生效（插件加载时把配置深拷贝冻结了），控制台能重载，但你得先知道要改什么、去哪改。
- 手上没有任何统计：现有计数是「本次启动以来」的内存数字，重启归零，也没有按群拆分。
- 手上没有消息级日志：收到消息基本不记，发出消息只在最啰嗦的调试级别记一句，所以「哪条消息被哪个插件处理、回了什么」无从查起。

## 二、目标 / 非目标 / 反目标

**目标**

1. 配置可见可改：每一项都有名称、含义、取值范围、默认值；改完保存并能重载生效。
2. 统计：收到/发出的消息数、按群拆分、各插件处理数；卡片展示「今日」与「累计」，另有近 7 天趋势和「今天谁在聊」。
3. 调试：喂一条消息看插件会做什么，默认只预览不真发；支持插件热重载。
4. 日志：记录收到、发出、插件处理、插件异常，可搜索可过滤，不同类型不同底色。
5. 插件可以自带你自己的页面（bga_plugin 需要「各群桌游 + 抓取状态 + 排行榜预览」一页）。

**非目标**

- 不做远程访问、多用户、账号体系。
- 不改动现有消息处理逻辑（只加埋点，不改判定、不改顺序）。
- 不把 bga 的配置迁进 `bot_config.json`（迁移风险高，且它是独立仓库）。
- 不做手机端适配。

**反目标（技术上能跑也算失败）**

- 机器人收发消息被管理台拖慢、卡顿或丢消息。
- 管理台改动导致消息行为变化（重复、丢失、顺序变化）。
- 调试页把测试内容真的发进了群。
- 页面上的数字与实际不符（例如把「本次启动以来」的数字当成「今日」展示）。

## 三、约束

- Windows 10/11 x64、64 位 Python（仓库已验证 3.13）；依赖极少，`requirements.txt` 现在只有 `pefile`。
- 管理台与机器人**同进程、同生命周期**（你选的「跟机器人一起启动」）。退出顺序沿用现有约定：先取消待发送、再停插件、再断连接、最后关成员库。
- 群消息表每天清空（`daily_clear`），统计**不能**依赖它。
- `plugins/bga_plugin` 是独立 git 仓库，被主仓库 `.gitignore` 排除，改动分开提交。
- 现有插件线程模型：主循环 + 控制台线程 + 原生接收线程 + 每插件一个线程。

## 四、已定下的决定（你确认过的）

1. 结构：左侧导航 + 右侧内容。
2. 配置页：紧凑行布局，每项一个 ❓，点开浮窗显示详细说明；默认值预填好。
3. 日志页：左边一列类型（带条数）+ 右边日志流；整行按类型铺底色——收到蓝、发出绿、插件处理紫、异常红、系统灰。
4. 统计：数字全部用卡片，「今日」和「累计」各一组；近 7 天趋势、今天谁在聊、各群表都要。
5. 调试：默认只预览插件会回什么、不真发；「真的发到微信」要显式打开，且页面刷新后自动关掉。
6. 统计数据与日志数据必须持久化。
7. 插件可以自带页面（bga_plugin 要有自己的一页）。
8. 四样附加功能全要：7 天趋势、今天谁在聊、插件自带页面、调试默认绝不真发。

## 五、页面结构

左侧导航：

```
概览            ← 统计
插件
  bga_plugin
    配置
    排行榜       ← 插件自带的页面
  echo
    （配置）
调试
日志
```

- **概览**：今日四张卡片（收到 / 发出 / 插件处理 / 异常）→ 累计四张卡片 → 近 7 天收到/发出柱状 → 今天谁在聊 → 各群表（今日与累计并列）→ 各插件表（状态、处理、异常、丢弃、最近错误）。
- **插件 → 配置**：顶部有启用开关和「保存并重载」按钮；下面是分区（账号 / 群与桌游 / 抓取……），每行「字段名 ❓ + 输入框」。
- **调试**：左边填插件、会话、发送者、内容；右边是结果（命中的插件、会回的文本、异常、耗时），另有一个「真的发」开关。
- **日志**：左边类型列表带条数，右边日志流，顶部搜索框和群/插件/时间过滤。

## 六、我的判断（你没指定、由我拍板的，可以推翻）

1. **技术选型**：服务端用 Python 标准库 `http.server` + 线程，前端用纯 HTML/CSS/JS，不引入任何依赖、不做打包。理由：仓库现在只有一个依赖，加个 Web 框架和构建链不成比例。
2. **访问方式**：只绑 `127.0.0.1`，不设登录。本机使用；同一台电脑上的其他程序访问得到，但外网访问不到。需要口令可以后加。
3. **端口**：默认 `8787`，被占用时自动顺延；启动时把完整地址打印到日志。控制台新增一条 `admin` 命令打印地址。不自动弹浏览器。
4. **开关**：`bot_config.json` 新增 `admin` 段（`enabled` 默认 `true`、`port` 默认 `8787`），跟着 `ConfigStore` 一起校验。
5. **统计库**：用独立的 `.runtime/admin_data.sqlite3`，不复用成员库。理由：成员目录是可以整体关掉的，统计不该被它牵连。
6. **累计口径**：从加上这个功能那天起算，之前的历史补不回来，页面上要写清楚。趋势也是同理——攒够 7 天才完整。
7. **日志保留**：默认 7 天或最多 20 万条，超出按时间删；系统级警告（队列满、连接失败等）也收进日志页，显示成「系统」类型。
8. **配置写回**：按插件声明决定写到哪——声明 `bot_config` 的写回 `bot_config.json` 的 `plugins.<名称>`（保留 `enabled`）；声明 `plugin_file` 的写回插件目录下那个文件（例如 `bga_config.json`），键支持 `account.email` 这种点路径。没声明的插件，配置页只给只读当前值和原始 JSON 编辑，并标明风险。
9. **密钥字段**：bga 密码、大模型 api_key 这类字段不在页面上回显明文；不修改就不写回。
10. **调试的实现**：构造一条假消息真实走插件流程，但把「发送」这一步拦成预览，这样插件代码是真的跑过一遍的，不只是猜。
11. **验证范围**：沿用仓库现有 `unittest` 命令，只补新增纯逻辑的用例（配置声明解析与校验、今日/累计聚合、日志过滤、预览模式拦截发送），不扩大测试面、不碰真实微信与大模型。

## 七、技术方案

### 7.1 启动与收尾

- 新增 `wxbot_framework/admin/`（服务端逻辑 + 静态页面）。
- `BotApplication.run()` 里启动：起一个守护线程跑 HTTP 服务；`BotApplication.stop()` 里按新加的收尾步骤先停服务（关监听、等在途请求、把缓冲区落盘），再走原有的取消发送 → 停插件 → 断连接 → 关成员库。
- 配置读 `bot_config.json` 的 `admin` 段；`enabled` 为假时完全不启动，也不建库。

### 7.2 数据层

独立库 `.runtime/admin_data.sqlite3`，三张表：

- `message_log`：一条消息或一次处理一行。字段含时间（UTC）、类型（receive / send / plugin / error / system）、会话 ID、发送者、插件名、是否群聊、是否通过白名单、摘要文本。
  索引按（类型 + 时间）和（会话 + 时间）建；默认保留 7 天且不超过 20 万行。
- `stats_total`：累计计数，按维度存（全局 / 按群 / 按插件）× 指标（收到 / 发出 / 处理 / 异常 / 丢弃）。
- `meta`：首次记录日期等。

- 「今日」的数字由 `message_log` 按北京时间当天 0 点起聚合得到。
- 「累计」的数字由 `stats_total` 累积，启动时读回内存，随每条记录自增。
- 写入走内存缓冲 + 定时落盘（约每秒一次），收发路径上不做同步落盘；退出时强制落盘。这样统计不会拖慢消息处理。

### 7.3 埋点（不改消息行为）

- **收到**：在消息进入框架的入口处记一条，带「是否通过白名单」标记；汇总默认只算通过的。
- **发出**：在发送的唯一收口处记一条（所有插件回复都走这里），并带上发起插件名。
- **插件处理**：每个插件处理完一条消息后记一条（插件名、耗时、这条消息有没有被它回复过）。
- **异常**：插件回调抛错时记一条错误摘要，堆栈仍写在原来的文本日志里。
- 计数与记录都在旁路进行，不改变分发顺序、不阻塞回调。

### 7.4 插件配置声明

`plugin.json` 增加一个可选的 `config` 段，形如：

```json
"config": {
  "source": "plugin_file",
  "file": "bga_config.json",
  "pages": [{ "key": "ranking", "title": "排行榜" }],
  "sections": [
    {
      "title": "账号",
      "fields": [
        { "key": "account.email", "label": "邮箱", "type": "text", "default": "",
          "help": "BGA 登录邮箱；留空则匿名模式，公开排行榜照样能看", "range": "字符串" }
      ]
    }
  ]
}
```

- 字段类型：文本 / 密码 / 整数 / 小数 / 开关 / 枚举 / 键值表（群→桌游这种）/ 原始 JSON。
- 保存前按声明校验（类型、范围、必填、枚举），再交由框架或插件原有的校验兜底——声明与实际校验必须一致。
- 保存后默认重载该插件（按钮就叫「保存并重载」）；也可以只保存不重载。
- 现有插件里只有 `echo.prefix`、`idiom_chain.member_names`、`chat_summary.chunk_chars` 属于「插件私有配置」，其余插件要么没有配置项，要么用的是成员库/大模型配置。

### 7.5 插件自带页面

- 静态文件：插件目录下 `web/` 里的 HTML/CSS/JS，框架挂到 `/plugin/<插件名>/...`。
- 数据接口：插件类可选实现 `on_web(action, params)` 返回 JSON，框架路由 `/api/plugin/<插件名>/<action>`。
- 进不进左侧导航由 `plugin.json` 的 `config.pages` 决定；没声明就不出现。
- 框架只负责挂载、路由和把结果交给页面，页面内容插件自己写。

### 7.6 调试

- 填会话 ID、发送者、内容 → 构造一条消息 → 真实走一遍**插件分发**（只进分发这一步，不经过白名单过滤、管理员拦截、人格切换和成员库写入，避免调试污染真实记录）。
- 结果页要标明：本次预览未经过白名单与管理员判定，命中情况可能比真实运行时乐观。
- 发送被拦成预览：结果里列出「会回复什么」，不真的发；「真的发到微信」是单独的开关，默认关、刷新复位。
- 结果同时列出「看过这条消息但没回复」的插件，以及异常与堆栈。
- 热重载复用现有的插件重载：框架重载时本来就会重新编译源码、换新实例，不需要新机制。
- **已知限制（要写在页面上）**：调试会真的改写插件的内部状态（比如成语接局的局面、BGA 的缓存与绑定），不是无副作用的沙盒。

### 7.7 日志页

- 数据源就是 `message_log`：收到 / 发出 / 插件处理 / 异常 / 系统五类。
- 系统类来自框架自身的日志：把警告及以上级别的记录也写进这张表（例如「插件队列已满」「等待微信连接」）。
- 搜索覆盖内容、会话 ID、发送者、插件名；过滤支持类型、群、插件、时间范围；日志流跟随最新，可以暂停翻历史。
- 颜色按你选的那套：收到蓝、发出绿、插件处理紫、异常红、系统灰。

### 7.8 权限与安全

- 只绑本机回环地址，不设登录。
- 管理台能以机器人的身份发消息（调试页的「真的发」开关、以及插件的启停与配置），不要把端口暴露到不可信网络。
- 密钥字段不回显明文。

## 十、明确不做的诱人改动

- 把成员库配置、大模型配置也搬进管理台（配置源迁移风险高，先不动）。
- 引入前端框架或打包链。
- 管理台远程访问、账号体系、操作审计。
- 消息历史长期归档与全文检索（只保留 7 天）。

## 十二、实施边界（文档审读后补定）

一位独立审读者读了这份文档并提出几个必须明确的点，处理如下：

1. **调试只走插件分发**：调试的假消息只进入插件分发，不经过白名单过滤、管理员拦截、人格切换和成员库写入，避免把测试消息写进真实群记录；结果页必须标注「未经过白名单与管理员判定」。这样也守住了你选的「不做任何真实动作」。
2. **允许在框架核心加一层薄埋点**：为统计归因与预览拦截，可以在插件管理器与发送收口上增加线程级的「当前插件 / 当前消息」上下文、处理完成信号与预览开关。前提是**不改变分发顺序、不改变回调语义、不阻塞回调**。这是本期唯一允许触碰核心消息路径的改动。
3. **调试不额外引入桩替机制**：不为了调试专门做假大模型、假网络（那会多开一套机制）。调试时插件对外的真实调用如何处理，见下方待确认项。
4. **配置校验兜底按现状呈现，不做备份回滚**：保存前按声明校验；插件自身的校验仍在它自己那一层。像 bga 这种「配置非法时只记一条警告、插件降级运行」的行为保持原样，但页面上要把「插件已降级 / 尚未配置」做成一等状态（插件列表和配置页都要显眼标出），而不是静默通过。
5. **「最活跃插件」按今日算**：各群表里的这一列取「今日」，数据来自消息记录表，不新增「群 × 插件」的累计交叉维度；同表的「最近一条」也取自消息记录表。

3. **调试时外部调用真实发生**（已确认）：调用大模型、访问 BGA 网络与登录都走真实路径，不为调试做桩替。因此调试页需要呈现等待状态与耗时，并说明这里可能花钱、可能触发 BGA 的限速；但调试仍然**不会把消息发到微信**（发送始终被拦成预览，除非显式打开开关）。

### 已确认项

- 调试时插件对外的真实动作**真实发生**（大模型、BGA 网络与登录），页面负责呈现等待、耗时与失败原因，并提示可能产生费用与限流。
