## 1. 意图与目的

框架目前没有统一的定时任务机制。插件要定时干活，只能自己起后台线程、自己定配置格式、自己判断"到点没到点"。BGA 插件的 `SnapshotWorker` 就是这样一处：每 60 秒轮询一次，靠"北京日期 + 配置里的 `daily_snapshot_hour`"判断是否到点，配置写在插件自己的 `bga_config.json` 里。框架对它的存在一无所知——`status`、`plugins` 命令都看不到它，没有开关，跑没跑、失败没有只能翻日志。

本次要做的是：**由框架统一承担定时任务的配置、调度与启停**，插件只负责注册"这个任务做什么、默认什么时候跑"；管理台上能看见全部任务并直接改时间、启停、手动跑一次。

触发场景：BGA 插件要每天定时把当前排行榜播报到群里，但没有地方管理这件事。

## 2. 目标（Must have）

1. 插件在加载时能向框架注册定时任务：任务名、调度表达式、回调。
2. 调度表达式同时支持 **5 字段 cron** 和**常用中文语义化写法**（每天 / 工作日 / 每周X / 每月D日 / 每N分钟 / 每N小时）。
3. 任务的调度时间与开关统一由框架配置（`bot_config.json`）管理，可覆盖插件代码里的默认值。
4. 框架负责到点判断与触发；**错过的时刻不补跑**（用户 2026-10-16 决定）。
5. 控制台能查看全部任务及其最近一次运行结果，能单独启停，能手动触发一次。
6. 任务回调在**所属插件自己的线程**里执行，与消息回调串行，不与消息处理并发。
7. 管理台能查看全部任务（含生效时间与最近一次结果），能改时间、单独启停、手动跑一次；与管理台既有页面同一套写法。

## 3. 非目标（Must NOT have）

- 不迁移 BGA 现有的 `SnapshotWorker`（作为后续独立改动，本次只做框架 + 一个新的播报任务）。
- 不做补跑：进程当时没运行、或当时不匹配，该次就不执行。
- 不做运行历史的持久化（只在内存里保存最近一次结果），管理台也只显示最近一次。
- 不支持秒级 cron，不支持 `L` / `W` / `#` / `?` 等扩展语法，不支持逐任务配置时区。
- 不做任务参数下发：任务要用的参数仍由插件自己的配置文件提供（例如 BGA 的 `groups`）。
- 不做多实例并发执行、不做分布式调度。
- 不在管理台为任务新增统计维度、新表或新的日志类型。

## 4. 反目标（即使技术可用也不做）

- 不因为"顺手"把 BGA 现有快照逻辑一起重构掉。
- 不在没有实际需求时预留工作流编排、任务依赖、重试策略等通用能力。
- 不为定时任务引入第三方调度库，也不为管理台页面引入前端框架或构建链。
- 不把定时任务的运行结果写进插件数据库或新的持久化文件。

## 5. 约束

| 约束 | 来源 |
|---|---|
| 时区固定为北京时间，不逐任务配置 | 框架已有 `members.py: BEIJING`；BGA 快照也按北京日期 |

## 7. 配置

```json
"plugins": {
  "bga_plugin": {
    "enabled": true,
    "tasks": {
      "daily_broadcast": {
        "enabled": true,
        "schedule": "每天 21:00"
      }
    }
  }
}
```

- `tasks` 是框架保留键；同层的其余键仍是插件自己的配置，插件行为不变。
- `schedule` 缺省时用插件代码注册时给的默认值；给出时覆盖默认值。
- `enabled` 缺省为 `true`。
- 结构校验（在 `ConfigStore.load` 中，报错文案沿用现有中文风格）：`tasks` 必须是 JSON 对象；每个任务名必须符合 `validate_name` 的字符集（与插件名同规则，非法即配置整体校验失败）；每个任务必须是对象；`enabled` 若存在必须是布尔；`schedule` 若存在必须是非空字符串。
- **两类 schedule 出错的处理不同**（本次拍板）：
  - 插件**代码里写死的默认** schedule 非法 = 编码错误，`register()` 抛错，插件加载失败并记入 `load_errors`——早暴露，不掩盖。
  - **配置里覆盖的** schedule 非法 = 用户配置笔误，**只让该任务不注册**（任务状态记为"配置错误"，日志报错，`tasks` 命令与管理台都可见），插件其余部分照常加载。理由：一个任务的笔误不应让插件已有命令全部失效。此时**不回退**到代码里的默认时间，避免"我改成 9 点，结果 21 点播了"。
- 通过管理台或命令行改时间/开关时，写入前先校验，写入走 `ConfigStore` 的原子替换（先读整份、只改一个键、再整体替换）——与现有插件启停同一机制。

## 8. 行为设计

### 8.1 调度表达式

先按语义化写法解析，解析不出再按 5 字段 cron 解析。语义化写法忽略空格：

| 写法 | 等价 cron | 含义 |
|---|---|---|
| `每天 HH:MM` | `M H * * *` | 每天一次 |
| `工作日 HH:MM` | `M H * * 1-5` | 周一至周五 |
| `每周一 HH:MM`（一…日） | `M H * * 1` | 每周固定一天 |
| `每月 D 日 HH:MM` | `M H D * *` | 每月固定一天 |
| `每 N 分钟` | `*/N * * * *` | 每 N 分钟 |
| `每 N 小时` | `0 */N * * *` | 每 N 小时 |

cron 为 `分 时 日 月 周` 五个字段，支持 `*`、`,`、`-`、`/`；周字段 0–7，0 与 7 都表示周日。`HH:MM` 必须是真实时刻（00–23 / 00–59）；`N` 必须为正整数，`每 N 分钟` 的 N ≤ 59。

同一个解析器还要能**正向推算下一次触发时刻**（供管理台显示"下次触发"）：按分钟向前找，最多找一年；找不到就返回空（表示这个表达式永远不会匹配）。

### 8.2 到期判断与触发

- 主循环每 0.5 秒 tick 一次（沿用 `runtime.py` 既有周期），全程只做内存比较，无网络与磁盘操作。
- 判断粒度是**分钟**：当前北京时间分钟与该任务的 cron 匹配、且这一分钟尚未触发过 → 触发。因此错过的时刻天然不会补跑。
- 进程内按（任务，分钟）去重。已知边界：若在同一分钟内重启进程，该分钟的任务可能再触发一次；本次不做持久化去重，文档与实现说明中写明。
- 上一轮尚未结束时，本次不触发也不排队（跳过），并计入跳过次数。

### 8.3 执行位置

任务回调投递到**所属插件自己的线程**：`PluginRecord` 增加一条任务队列，与消息队列共用同一个回调锁。结果是同一插件的任务回调与消息回调互不重叠，任务也不会占用框架主循环线程。代价是一次长时间任务会推迟该插件后续消息的处理——与现有"插件内同步 HTTP 会阻塞该插件消息"的性质一致。

### 8.4 注册契约

插件在 `on_load(ctx)` 中注册：

```python
def on_load(self, ctx):
    ctx.tasks.register("daily_broadcast", "每天 21:00", self._broadcast)
```

- 任务名规则同 `validate_name`，在同一插件内唯一；重复注册同名任务报错。
- 回调签名 `callback()`，无参数；需要的上下文由插件自行闭包携带（例如把 `ctx` 绑进去）。
- 只允许在 `on_load` 期间注册，其它时机注册报错。
- `register()` 在任务名非法或默认 schedule 解析失败时抛 `ValueError`（见 §7 第一类）。
- 插件停用或卸载时其任务随之注销；重新启用后按最新配置重新注册。

### 8.5 失败处理

- 任务回调抛异常：记录该任务最近一次结果为失败（含异常摘要与耗时），写 `Plugin.<插件>` 日志；**不影响该插件处理消息，也不影响其它任务**。
- 微信未连接时 `ctx.send_text` 会抛错，同样记为失败；**不重试、不补跑**。
- 调度器 tick 自身的异常不得冒到主循环。
- 插件加载完成后，框架对比"配置里声明过的任务名"与"代码实际注册的任务名"：配置里多出来的记一条 warning（提示写错或插件已不再提供该任务），不影响加载。

### 8.6 控制台命令

| 命令 | 行为 |
|---|---|
| `tasks` | 列出任务：插件 / 任务 / 生效的 schedule / 状态 / 上次运行时间与结果 / 跳过次数 |
| `enable <插件> <任务>` | 打开并写回配置 |
| `disable <插件> <任务>` | 关闭并写回配置 |
| `run <插件> <任务>` | 立即手动执行一次（忽略开关状态），用于验证 |

- `tasks` 的行集合 = **已注册的任务** ∪ **配置里声明过的任务名**（与 `PluginManager.status()` 取 `specs ∪ records` 的做法一致），因此配置里写了、代码里没有的任务也能被看见，状态标为"未注册"；插件被停用/未加载时，其任务标为"未加载"。
- `enable` / `disable` 只写配置，不要求插件当前已加载；任务名需合法（否则报错）。
- `run` 要求该任务当前已注册，否则报错。
- `help` 的提示行同步补上这些命令。插件级的 `enable <插件>` / `disable <插件>` 行为不变。

### 8.7 可见性与日志

任务维度由 `tasks` 命令与管理台页面输出，不改变 `status` 命令既有的 JSON 结构（避免影响现有输出）。框架日志沿用 `Plugins` logger 记录任务注册/注销/配置错误，任务运行结果写 `Plugin.<插件>` logger。任务失败本身会以 WARNING/ERROR 落入文本日志，管理台的系统日志旁路会自动把它显示在「日志」页的「系统」类，不需要为任务新增日志类型。

## 9. 管理台中的定时任务页

管理台（`wxbot_framework/admin/`）与机器人同进程，只绑 `127.0.0.1`，不设登录；前端是无框架的哈希路由单页，核心页面的入口写在 `app.js` 里，插件的自带页面才由数据驱动。定时任务是**框架级**资源（跨插件），因此做成本核心页面，而不是插件页——插件页机制（`plugin.json` 的 `config.pages` + 插件类的 `on_web`）只适合"某个插件自己的页面"。

### 9.1 页面与导航

- 左侧导航在「概览」之后、「插件」分组之前新增一条「定时任务」（`#/tasks`）。
- 页面一行一个任务，列出：插件 / 任务名 / 生效 schedule（并标注来源是"代码默认"还是"配置覆盖"）/ 开关 / 状态 / 上次运行时间与结果 / 跳过次数 / 下次触发时间。
- 行内操作：开关、改时间并保存、立即执行一次。没有任务时给明确的空状态文案。

### 9.2 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/tasks` | 全部任务（跨插件）+ 最近一次运行结果 + 下次触发时间 |
| POST | `/api/tasks/<插件>/<任务>/toggle` | 启停并写回配置 |
| POST | `/api/tasks/<插件>/<任务>/schedule` | 改时间：先用与注册时同一个解析器校验，再写回配置 |
| POST | `/api/tasks/<插件>/<任务>/run` | 立即执行一次（忽略开关） |

路径用框架级前缀 `/api/tasks/...`，不嵌在 `/api/plugins/<名>/...` 下：任务列表是跨插件的，而且现有 `/api/plugins/<名>/<动作>` 是两段式解析，嵌套会与它打架。

### 9.3 与命令行、配置的关系

- 页面开关与命令行的 `disable <插件> <任务>` 写的是**同一份配置**（`bot_config.json` 的 `plugins.<插件>.tasks.<任务>.enabled`），走同一条代码路径；两边不各写一套。
- **改时间不需要重载插件**：时间由调度器持有，保存成功后即在该任务的下一次到期判断中生效，插件实例、会话与内部状态都不受影响。理由：重载插件会打断正在处理的命令并重建插件状态（BGA 会重建会话与库连接），代价远大于改一个时间。
- 页面保存前用与注册时**同一个**解析器校验；校验不过直接返回错误、不写盘，因此页面不会写出非法 schedule（手改配置文件仍可能写出非法值，那条路径按 §7 处理）。

### 9.4 可见性

- 任务列表口径同 §8.6：已注册任务 ∪ 配置里声明过的任务名；插件未加载时标为"未加载"，配置里写了但代码没有的任务标为"未注册"。
- 运行历史只在内存保存"最近一次"，管理台不做持久化，也不往统计库新增表或新的日志类型。
- 插件的任务与插件自身的启停状态一致：插件被停用后，它的任务在页面上显示为未加载，也不会触发。

### 9.5 落点

- `wxbot_framework/admin/api.py`：`_route` 增加四个分支，新增 `_tasks_view`、`_task_toggle`、`_task_schedule`、`_task_run`；`AdminApi.__init__` 增加调度器参数。
- `wxbot_framework/admin/web/app.js`：`currentRoute()`、`buildNav()`、`route()` 各加一处，新增 `renderTasks`。
- `wxbot_framework/runtime.py`：`start_admin()` 里把调度器注入 `AdminApi`。
- `wxbot_framework/config.py`：新增任务开关与任务时间的原子写方法（与 `set_enabled` 同形态）。
- `admin/server.py`、`index.html` 不用改：`/api/` 前缀自动转发，静态目录与页脚不受影响。

## 10. 本次的落地用例：BGA 每日排行榜播报

这是本设计的第一个使用者，用来验证机制可用。

- 任务名 `daily_broadcast`，注册在 `plugins/bga_plugin` 的 `on_load` 中，默认调度 `每天 21:00`（可用 `bot_config.json` 或管理台页面覆盖）。
- 播报目标（用户 2026-10-16 决定）：对 `bga_config.json` 中 `groups` 配置的**每个群各播一条**，各播该群所配桌游的排行榜；`groups` 里没配的群不播，私聊不播。
- 播报内容（用户 2026-10-16 决定）：与该群 `/bga排行榜` 命令**完全一致**的取数路径、条数上限与字节预算规则，不新造第二套口径。
- 发送目标与桌游映射从插件自己的 `bga_config.json` 读取，不经过框架配置。
- 缺少可用登录、或该群所配桌游取不到排行榜时，按该命令原有的失败提示口径处理并留痕；不特殊处理、不重试。
- 本次**不**改动 BGA 现有的每日快照线程。
- 注意：`plugins/bga_plugin` 是独立 git 仓库，主仓库整体忽略它；本次要改动该仓库并在其中提交。

## 11. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 同一分钟内重启进程可能重复触发 | 重复播报 | 已知边界；文档写明，本次不做持久化去重 |
| 长时间任务推迟该插件消息回复 | 体验下降 | 与现有同步 HTTP 行为一致；任务与消息不并发 |
| 微信断线时任务失败 | 该次播报丢失 | 记为失败并留痕；按用户决定不补跑 |
| 语义化写法写错（漏字、非法时刻） | 该任务不触发 | 页面提交前拒绝；配置文件里的非法值只让该任务不注册并在页面显示为配置错误，不影响插件其余功能 |
| 页面与命令行同时改同一份配置 | 互相覆盖 | 两边都走"先读整份、只改一个键、原子替换"，与现有插件启停同一机制 |
| 改时间后不重载插件，插件内的默认值仍是旧值 | 用户以为没生效 | 列表显示生效值与来源；改完即时生效，不需要重载 |
| 主循环 tick 增加开销 | 可忽略 | 每 0.5 秒一次，仅内存比较 |

## 13. 验证策略（最小）

**业务规则核对清单**（由第三方逐条核对是否落实）：

1. 语义化写法与 cron 都按北京时间解释；`每天 21:00` 与 `0 21 * * *` 等价。
2. 只有当前分钟匹配才触发；错过的时刻不补跑。
3. 任务回调在所属插件自己的线程内执行，且与消息回调串行、不重叠。
4. 上一轮尚未结束时，到点不再触发。
5. `schedule` 覆盖插件代码里的默认值；`enabled=false` 时不触发。
6. 插件停用或卸载后其任务不再触发，重新启用后恢复。
7. 任务抛异常只影响该任务的结果记录，不影响插件处理消息与其它任务。
8. `tasks` 能列出全部任务与上次运行结果；`enable` / `disable` / `run` 按 §8.6 生效。
9. 配置里覆盖的 schedule 非法时，该任务不注册且插件其余功能照常可用，`tasks` 能看到该任务处于配置错误状态；插件代码里的默认 schedule 非法时插件加载失败。
10. 配置里声明但代码未注册的任务名，能在 `tasks` 中被看到（标为未注册），并有一条 warning 日志。
11. BGA 播报只发到 `bga_config.json` 的 `groups` 里配置过的群，每个群播的是该群所配桌游的排行榜，内容与 `/bga排行榜` 同口径。
12. 管理台「定时任务」页能列出全部任务与上次结果；页面上的开关与改时间写回 `bot_config.json` 的对应键，且命令行/重载后看到的状态与页面一致。
13. 页面改时间后不需要重载插件即生效（下一次到期判断按新时间）；页面提交非法时间被拒绝且不写盘。

**确定性代码核对**：用针对性样例核对调度表达式解析、分钟匹配与"下次触发时刻"推算（不做全量回归）。运行需用户单独授权。

不扩张为回归测试、覆盖率或代码审查。
